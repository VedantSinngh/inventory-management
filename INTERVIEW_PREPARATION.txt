Q1: How does the real-time update system work? Walk me through what happens when 
    an order is created.

A: Good question. Here's the complete flow:

When a user fills out an order form in React and submits it, the frontend makes a 
POST request to /api/orders with the order data and includes the JWT token in the 
Authorization header.

On the backend, that request hits the protect middleware first, which extracts the 
token, verifies the signature using the JWT_SECRET, and fetches the user from the 
database. If anything fails, it returns 401 Unauthorized immediately.

Then the order goes through input validation - we check that the order type is either 
PURCHASE or SALES, that items array is not empty, each item has a valid product ID, 
quantity is positive, things like that. If validation fails, 400 Bad Request.

If validation passes, the business logic kicks in. This is where I implemented 
transactions. The code tries to start a MongoDB transaction session. If the database 
supports it - like MongoDB Atlas, which always has replica sets - then we're inside a 
transaction. We lock the database for the duration of these operations.

Inside the transaction: for each item in the order, we query the Product, check if 
current stock is >= requested quantity. If not, we abort the entire transaction and 
return an error. If yes, we atomically deduct from the product's stock using MongoDB's 
$inc operator. We create an AuditLog entry recording the STOCK_OUT action. We create 
the Order document.

Then we commit the transaction. Either all of those operations succeed together, or 
none of them do. That's what prevents overselling.

If transactions aren't supported, the code catches that specific error and falls back 
to non-transactional mode - we still create the order, but without the atomic guarantee. 
It's not ideal, but it's better than crashing.

After the order is saved, the backend calls a global function called 
global.emitShipmentUpdate(shipmentId, {...data}) which is a Socket.IO emit.

Socket.IO has this concept of "rooms" - you can think of them like chat channels. We 
have a room called 'shipment-{id}' for updates about that specific shipment, and a 
'dashboard' room for global inventory visibility. The emit sends the order data to all 
connected sockets in those rooms.

On the frontend, components that care about shipment updates have listeners:
socket.on('shipment-update', (data) => setShipment(data))

When they receive that event, they update their state, React re-renders, and users see 
the new order instantly. No page refresh needed.

If Socket.IO connection drops - bad network, browser tab closed, whatever - the 
disconnect event fires and the socket is cleaned up from memory. When the user 
reconnects, they rejoin the rooms they care about.


Q2: You mentioned implementing MongoDB transactions as a solution. What was the 
    problem you were solving, and why is this the right fix?

A: The problem is called a race condition or concurrency issue. Here's the scenario:

Imagine a product with exactly 5 units in stock. Two orders come in at basically the 
same time, each wanting to buy 5 units.

Without transactions, here's what happens:
- Order A queries the product, sees stock = 5, passes the check
- Order B queries the product, also sees stock = 5, passes the check
- Order A deducts 5, stock becomes 0
- Order B deducts 5, stock becomes -5 (you just sold 10 units when you only had 5)

This is called overselling or inventory underflow.

Transactions solve this by making the whole operation atomic - indivisible. Think of it 
like a lock. When the transaction starts, it locks that product record. Order A gets 
the lock, reads stock = 5, deducts 5, releases the lock. Then Order B gets the lock, 
reads stock = 0, fails the check, rolls back. This is guaranteed by the database, not 
by my code.

Now, MongoDB transactions require a replica set - you can't use them with a standalone 
MongoDB server. The first time someone tried to run this on a local MongoDB instance, 
the transaction would fail with an error like "Transaction numbers are only allowed on 
a replica set member."

Rather than just crash, I added graceful fallback logic. The code catches that specific 
error message and if it matches a list of known "transactions unsupported" errors, it 
re-runs the operation without a transaction. It's not atomic, but at least it still 
works for development.

In production, you'd use MongoDB Atlas or a self-hosted replica set, so transactions 
always work. The code handles both scenarios.

Is this perfect? No, ideally you'd always have transactions. But it's pragmatic - the 
system works in development and has full protection in production.


Q3: Walk me through the security measures you implemented and why you chose them.

A: I approached security from multiple angles because you're dealing with inventory data 
and financial transactions.

First, authentication and authorization:
- JWT tokens with 30-day expiry. The token only contains the user ID, so when someone 
makes a request, we fetch the user from the database each time to get their current 
role. This way, if I revoke someone's admin access, they can't use an old token to 
stay admin.
- Passwords are hashed with bcryptjs using 10 salt rounds. The pre-save hook on the 
User model automatically hashes passwords, so developers can't accidentally store 
plaintext passwords.
- Rate limiting on login: 5 attempts per 15 minutes per IP address. Prevents brute 
force attacks.
- Role-based access control with three roles: ADMIN, MANAGER, STAFF. Some endpoints 
require specific roles, checked with authorize('ADMIN', 'MANAGER').

Second, input validation and sanitization:
- Every POST and PUT endpoint validates incoming data with express-validator. We check 
types, lengths, formats. Email must be valid email format, product quantity must be a 
positive integer, MongoDB IDs must be valid ObjectIds. We reject any malformed request 
before it touches the database.
- This prevents NoSQL injection attacks where someone might pass {$ne: null} in a query 
to bypass validation.

Third, network security:
- Helmet middleware adds security headers: X-Frame-Options to prevent clickjacking, 
Content-Security-Policy to prevent script injection, X-Content-Type-Options to prevent 
MIME sniffing.
- CORS is configured with a whitelist - only specific origins are allowed. In 
development, I allow localhost. In production, only the actual frontend domain.
- Socket.IO requires a valid JWT token to connect - unauthenticated connections are 
rejected.

Fourth, data storage:
- JWT tokens are stored in sessionStorage on the frontend, not localStorage. 
SessionStorage clears when you close the browser tab, so tokens have limited lifetime. 
An attacker who finds JavaScript code on another website can't read sessionStorage 
from your domain.
- Environment variables are validated at startup. If JWT_SECRET is missing or less than 
32 characters, the entire application refuses to start. This prevents deploying with a 
weak secret by accident.

Fifth, audit logging:
- Every action - create, update, delete, stock change, approval - is logged to the 
AuditLog collection with user ID, timestamp, entity type, entity ID, and change details.
- For compliance and debugging, you have a complete history of who did what.

Sixth, soft deletes:
- No hard deletes. When you delete a product, we just set deletedAt to current 
timestamp. All queries filter WHERE deletedAt IS NULL. This preserves data for audit 
and recovery, and maintains referential integrity - you won't break orders that reference 
a deleted product.

I didn't implement HTTPS redirect because that's typically done at the reverse proxy 
or platform level, not in the app. Same with HttpOnly cookies - on the frontend we're 
using sessionStorage and fetch headers, not cookies.

Is every possible vulnerability covered? No, nothing is perfectly secure. But this is 
defense in depth - multiple layers so if one fails, others catch the attack.


Q4: What was the most challenging technical problem you faced, and how did you solve it?

A: The MongoDB transactions fallback I mentioned was hard, but honestly, the most 
challenging was designing the schema to support all the real-world inventory use cases 
without creating N+1 query problems or massive document sizes.

Here's what made it complex: a warehouse needs to track products, but products have 
batches, batches have expiry dates and storage conditions, products have suppliers, and 
orders contain items that reference products and optionally batches.

If I made batches a sub-array within Product documents, those documents could grow to 
megabytes in size as you add thousands of batches. MongoDB has a 16 MB document size 
limit, and more practically, pulling that entire product into memory just to read one 
field is wasteful.

If I made batches a separate collection and didn't carefully think about queries, I'd 
end up with N+1 problems - to get 20 products with their batches, I'd query products 
(1 query), then for each product query its batches (20 more queries). 21 queries total.

My solution: Batches are a separate collection with a reference to the Product. When 
I need products with their batches, I use Mongoose populate() with careful limits. I 
don't deeply populate - I don't populate supplier.products or user.orders, because 
those references point back creating circular references. I stop at 2 levels deep.

For the Product model specifically, I added 15 strategic indexes:
- By category, warehouse, SKU (for lookups)
- By stock + lowStockThreshold (for low stock queries)
- By ABC classification and sales velocity (for demand forecasting)
- By deadStock flag and autoReorder flag (for system recommendations)
- By creation date (for sorting)

Each index takes memory and slows down writes slightly, but massively speeds up reads. 
I chose these indexes by analyzing the actual queries the application makes. What does 
the dashboard query for? What does the low stock alert query for? Index those.

Testing this was hard because I didn't have gigabytes of production data. I seeded the 
database with thousands of products and orders and ran slow-query logs to see which 
queries were taking too long.

The result: product queries that would have taken seconds now complete in milliseconds, 
even with thousands of products. It's a tradeoff - the schema is a bit denormalized, 
and developers have to be careful about circular references - but it's the right 
tradeoff for an inventory system where reads far outnumber writes.


Q5: Why did you choose the MERN stack specifically? What are the tradeoffs?

A: I chose MERN for several reasons aligned with building a production system:

MongoDB because it's schema-flexible and scales well with Atlas. Inventory systems need 
to store different kinds of entities - products are different from shipments are 
different from suppliers. MongoDB lets you store complex nested objects without 
migration headaches.

Express is minimal and unopinionated. I could structure the code however made sense for 
inventory domain logic - separate route files, separate service files, separate models. 
No "Rails magic" fighting you.

React for the frontend because state management is critical for a dashboard application. 
Multiple users changing inventory, orders coming in, real-time updates - React's 
declarative rendering means I think about what the UI should be, not how to update the 
DOM. Combined with Context API for simpler state management (rather than Redux), it's 
straightforward to sync with Socket.IO events.

Node.js runs on the same language - JavaScript - across backend and frontend. It's 
single-threaded with an event loop, perfect for I/O-heavy applications like an inventory 
system that's constantly reading/writing to MongoDB and pushing Socket.IO updates.

The tradeoffs:

MongoDB is eventually consistent, not strongly consistent. Transactions help but there's 
still edge cases. A relational database with ACID guarantees would be stronger, but 
MongoDB Atlas is easier to set up and scale.

Node.js is single-threaded, so CPU-intensive work blocks the event loop. If I was doing 
heavy analytics on millions of records, Python or Go would be better. But inventory 
operations are I/O-bound, not CPU-bound, so Node's fine.

React adds client-side complexity. You need to think about state, context providers, 
component lifecycle. A server-rendered framework like Django would be simpler, but 
wouldn't give you real-time updates as easily.

I avoided GraphQL in favor of REST because REST is simpler for a first version and the 
API structure maps cleanly to inventory operations. GraphQL would be better if the 
frontend needed lots of flexible queries, but a dashboard generally knows exactly what 
data it needs.

Overall, MERN is a good "all-purpose" stack. It's not optimal for any single use case, 
but it's solid for a full-featured production application where you need a scalable 
database, a flexible backend, and a rich frontend. Plus, it's widely adopted, so hiring 
and maintenance are easier.


Q6: How would you extend this system to handle a million products across 100 warehouses?

A: That's a real scale question. Current system would struggle. Here's what I'd do:

Database:
- Database sharding. MongoDB can partition data by warehouse or product category across 
multiple servers. So warehouse A's data lives on server 1, warehouse B's on server 2. 
Queries for a single warehouse are fast because they hit one shard.
- Redis caching layer in front of frequently-accessed data: current stock levels, 
product details, popular items. Reduces database load.
- Archive old audit logs to a separate collection or data warehouse. Keep recent logs 
in the hot collection for performance.

Backend:
- Horizontal scaling: run multiple Node.js instances behind a load balancer. Each 
instance is stateless. For Socket.IO, I'd add a Redis adapter so socket messages route 
correctly across instances (currently Socket.IO is single-instance only).
- Asynchronous jobs: demand forecasting and anomaly detection are CPU-heavy. Move these 
to background job queue (Bull with Redis) so they don't block request handling.
- API rate limiting by user, not just by IP. Prevent one user from monopolizing resources.

Frontend:
- Lazy load components. Instead of loading all 100 warehouses at once, load the one 
the user selected.
- Virtual scrolling for product lists. Instead of rendering 10,000 rows, only render 
the 20 visible rows.
- Service worker for offline caching. If network is slow, show cached data.

Monitoring:
- Add distributed tracing (Jaeger or DataDog) to see bottlenecks.
- Add alerting on high latency so you catch problems before users do.
- Database query monitoring to catch slow queries automatically.

This would be a multi-month effort, easily. Current architecture assumes everything 
fits in one database and one application server. For a million products, you'd need to 
redesign significantly.


Q7: Walk me through your approach to debugging a real production issue. Say a customer 
    reports that orders are randomly failing with "Insufficient stock" even though 
    the dashboard shows plenty of stock.

A: This is a real issue I've designed for. Here's my systematic approach:

Step 1: Understand the problem
- Ask the customer: When did this start? One order failing or many? Is it specific 
products or all products? Specific warehouses? Specific users? Rough frequency?

Step 2: Reproduce locally
- Try to create the same type of order in development with similar data. Can I make it 
fail? If I can, it's deterministic. If I can't, it's probably concurrency or data 
corruption.

Step 3: Check the audit logs
- Query the AuditLog collection for that product and user around the timestamp of the 
failed order. Look for STOCK_OUT entries. Was stock actually deducted before? Is there 
a discrepancy between what the dashboard shows and what the database shows?
- Example query: db.auditlogs.find({entityId: productId, createdAt: {$gt: timestamp}})

Step 4: Investigate the order failure
- Look at the Orders collection. Find failed orders. Check the error message returned 
to the frontend. Is it "Insufficient stock" or something else?

Step 5: Check for concurrent orders
- This is the key insight. If I see "Dashboard shows 100 units, but three orders for 
30 units each all tried to place simultaneously and one failed," that's a concurrency 
issue even with transactions.
- Query: db.orders.find({type: 'SALES', items.product: productId, createdAt: 
{$gt: startTime, $lt: endTime}})
- Add up the quantities. If they exceed stock, one order must fail.

Step 6: Verify transaction support
- Connect to the MongoDB instance and run: db.serverStatus().replication
- If it shows "ismaster: true" and "members", transactions are supported.
- If it shows "replication not running" or similar, transactions are falling back to 
non-transactional mode, which doesn't guarantee atomicity.

Step 7: Check for data corruption
- Query the product document:
  db.products.findOne({_id: productId}, {stock: 1})
- Compare with sum of orders:
  db.orders.aggregate([
    {$match: {items.product: productId, type: 'SALES'}},
    {$group: {_id: null, totalSold: {$sum: '$items.quantity'}}}
  ])
- If stock + totalSold doesn't match initial stock, there's data corruption. Probably 
from a failed deployment or manual database edit.

Step 8: Check for other systems modifying stock
- Search the codebase for places that directly modify product.stock without going 
through the order creation flow. Maybe there's a data migration script or manual 
endpoint that's not audited.
- grep -r "stock.*=" backend/routes/

Step 9: Check network/synchronization issues
- Is the frontend making multiple order submissions due to a double-click or auto-retry? 
Check the browser network tab (DevTools). Are multiple POST requests being sent?

Step 10: Deploy a fix or workaround
- If it's a concurrency issue, ensure MongoDB is configured as a replica set.
- If it's data corruption, write a script to reconcile stock from audit logs.
- If it's a code bug, write a test that reproduces it, fix the code, deploy.

The key advantage of audit logging is that I can reconstruct exactly what happened, 
step by step, which makes debugging production issues much faster.


Q8: Describe the architecture of your anomaly detection system. What kinds of anomalies 
    can it detect?

A: The anomaly detection service analyzes stock movements in the audit log and identifies 
three types of suspicious activity:

Volume Anomalies:
The system calculates the mean and standard deviation of stock movement quantities over 
the last 24 hours. If a single movement is more than 3 standard deviations from the mean 
- meaning it's statistically extremely unlikely under normal operations - it flags it.
Example: If daily movements average 5 units +/- 2 units, and suddenly there's a 50-unit 
movement, that's a red flag. Could be legitimate (seasonal rush) or theft.

Frequency Anomalies:
Instead of looking at movement size, look at how often they happen. If normally there's 
5-10 movements per day, but suddenly there's 50 movements in 2 hours, that's suspicious. 
Could indicate someone rapidly trying to move stolen goods.

Pattern Anomalies:
Look at timing. If all movements happen during business hours (9 AM to 5 PM) normally, 
but suddenly you see movements at 3 AM, that's anomalous. Also cluster movements - 
several rapid movements in short time window.

When an anomaly is detected, the system creates an Alert document with:
- Type: 'ANOMALY_DETECTED'
- Severity: LOW, MEDIUM, HIGH, or CRITICAL (based on the magnitude of the anomaly)
- Related entity: Which product was affected
- Metrics: Current value, threshold value, deviation percentage

The alert is then broadcast to dashboards via Socket.IO so managers see it in real-time.

The sensitivity threshold is configurable - MEDIUM uses 3 standard deviations, HIGH uses 
2 (catches more anomalies but might have false positives), LOW uses 4 (only catches 
extreme anomalies).

This isn't foolproof. If someone is smart about how they steal - moving 4 units at a 
time instead of 50 - they could stay under the threshold. But it catches the obvious 
cases and alerts a human to investigate further. It's designed to complement, not 
replace, human audit.


Q9: Tell me about the forecasting system. How accurate is it, and what are the limitations?

A: The forecasting service analyzes historical sales data and predicts future demand 
using multiple algorithms.

How it works:
1. Query the Orders collection for the past 12 months (configurable)
2. Aggregate by time period (daily, weekly, or monthly) to get sales volumes
3. Run statistical algorithm
4. Calculate accuracy using MAPE (Mean Absolute Percentage Error)
5. Generate confidence intervals - not just "sell 100 units next month" but "sell between 
80 and 120 units with 95% confidence"

The algorithms:
- Simple Moving Average: Just the average of the last 3 months. Super simple, useful baseline.
- Weighted Moving Average: Recent months weighted higher (50% recent, 30% middle, 20% old). 
Captures trends better.
- Exponential Smoothing: Uses alpha factor (0.3) to weight recent data, with exponential 
decay. Good for data with consistent trends.

Accuracy:
MAPE below 10% is considered very good. Most of my forecasts hit 5-15% MAPE, which is 
reasonable for consumer goods. If you have volatile products or strong seasonality, 
accuracy drops to 20-30% MAPE.

I return both a point estimate ("expect 100 units") and a confidence interval ("90% 
confidence range is 80-120").

Limitations:
1. Requires 3 months minimum data, preferably 12 months. New products can't be forecasted 
until they have sales history. Solution: use default static forecasts or manager input.

2. Can't handle black swan events - if you launch a viral marketing campaign or a 
competitor closes, historical data becomes irrelevant. The algorithm sees the spike and 
thinks demand is stable at high level, but it's temporary.

3. Ignores external factors by default. If there's a holiday, promotion, or weather 
event, the algorithm doesn't know. You can optionally pass these as factors, but it 
requires manual input.

4. Seasonality detection needs 12 months of data minimum. If I try to detect seasonality 
with 6 months of data, I'm comparing apples to oranges (one winter vs another winter).

5. Assumes linear or exponential trends. For products with complex, non-linear patterns, 
this breaks down.

What I'd do next:
- Implement ARIMA (autoregressive integrated moving average) for better trend detection
- Add holiday/promotion calendars so the system knows about external events
- Use machine learning (neural networks) for products with complex patterns, but this 
requires even more data
- Integrate external data APIs (weather, news, social media trends) to improve 
prediction

But for a first version, these simple algorithms cover 80% of use cases.


Q10: If you were starting this project over knowing what you know now, what would you 
     do differently?

A: Several things:

Database:
- Use PostgreSQL instead of MongoDB. Inventory is relational - products belong to 
categories, orders have line items, shipments track orders. SQL constraints (foreign 
keys, unique constraints) would prevent data corruption. MongoDBs flexibility is nice 
for prototyping but adds complexity for enforcing data integrity.

Testing:
- Start with tests from day one. Write unit tests for business logic, integration tests 
for API endpoints, E2E tests for critical user flows. Currently I have zero automated 
tests, which means I'm not catching regressions.

Architecture:
- Use TypeScript instead of plain JavaScript. I caught several bugs during this session 
that a type checker would have caught immediately. Runtime errors are expensive.
- Implement proper dependency injection so services don't depend directly on models. 
Makes testing easier and code more modular.

Frontend:
- Use a router with proper state management (Redux, Zustand) instead of Context API. 
Context is fine for small apps, but with 20+ pages and complex interactions, it gets 
messy.
- Add proper form library (React Hook Form) instead of manual form state. I'm reinventing 
the wheel.

DevOps:
- Use Docker from the start, not as an afterthought. Would have caught environment 
issues earlier.
- Set up infrastructure-as-code (Terraform) so I can spin up production-like environments 
easily.

API:
- Add OpenAPI/Swagger documentation automatically. I documented the API in the README, 
but it's manual and easy to get out of sync.

I'd keep the overall architecture - separate backend and frontend, REST API, real-time 
updates with WebSocket. But the execution would be cleaner with these changes.

SECTION 5 — GLOSSARY
================================================================================

Define these terms in plain, simple English for non-technical interviewers:

1. MERN STACK
A set of four technologies that work together to build web applications: MongoDB 
(database), Express (backend web server), React (frontend interface), Node.js 
(JavaScript runtime). Think of it as the complete toolbox - the warehouse (database), 
the workers (backend), and the office (frontend).

2. REST API (Representational State Transfer)
A way for the frontend and backend to talk to each other. Instead of one giant 
conversation, they break it down into specific requests: "Give me the product list," 
"Create a new order," "Update this shipment." Each request is small and focused.

3. JWT TOKEN (JSON Web Token)
A secure digital ticket that proves you're logged in. When you log in, the server 
gives you a unique token. Every time you make a request, you show your token. The 
server verifies it hasn't been tampered with. It's like a concert wristband - proves 
you paid and got in.

4. MONGODB
A database that stores information in a flexible format (documents), not rigid tables. 
Instead of a spreadsheet with fixed columns, it's like a filing system where each 
folder can have different contents.

5. SOCKET.IO
A technology that pushes updates from the server to your browser in real-time. Instead 
of constantly asking "Is there any news?" (refreshing), the server tells you the moment 
something changes. It's like a news alert rather than checking the news website every 
minute.

6. TRANSACTION
An all-or-nothing operation. Either everything succeeds or nothing happens. Like a 
bank transfer - money either leaves your account and arrives in the other account, or 
the transfer fails and your money stays. Never a state where money disappears.

7. ANOMALY DETECTION
Finding unusual or unexpected patterns in data. If orders always happen during business 
hours, but suddenly there's one at 3 AM, that's anomalous. It could be legitimate or 
suspicious - the system flags it for a human to check.

8. AUDIT LOG
A complete record of who did what and when. Like security camera footage for data. 
Every action is recorded: "User John approved order #123 at 2:30 PM on Tuesday." Used 
for compliance and debugging.

9. SOFT DELETE
Instead of permanently erasing data, mark it as deleted but keep it in the database. 
Like moving a file to trash rather than permanently deleting it. Lets you recover data 
and maintain history.

10. RATE LIMITING
Restricting how many times someone can do something in a time window. "You can try to 
log in 5 times per 15 minutes." Protects against attackers trying thousands of passwords.

11. DEMAND FORECASTING
Predicting how much inventory you'll need in the future based on past sales. Like a 
weather forecast but for sales: "Based on last year, expect 200 units next month."

12. SCHEMA
The structure or blueprint for how data is organized in the database. Like a form with 
specific fields - product has name, SKU, price, stock. The schema defines what fields 
exist and what type of data goes in each.

SECTION 7 — THE BEST THING YOU DID (Most Important)
================================================================================

Identify the single most impressive technical contribution in the entire codebase:

THE BEST THING: MongoDB Transactions with Graceful Fallback for Concurrent Stock Operations

WHY THIS IS THE MOST IMPRESSIVE:

A) TECHNICAL VERSION (for a technical interviewer):

"The most impressive thing I did was solve the concurrent order problem with MongoDB 
transactions and graceful degradation.

The core issue: when two orders for the same product arrive simultaneously, both pass 
the initial stock check, and then both deduct from stock, resulting in overselling. 
This is a classic race condition in concurrent systems.

My solution in orderRoutes.js (lines 22-50):

I implemented a runWithOptionalTransaction() wrapper that:
1. Attempts to start a MongoDB session and transaction
2. Executes the entire order creation within that transaction (reads product, checks 
   stock, deducts stock, creates order)
3. Commits the transaction if everything succeeds
4. If transactions fail (not supported on this MongoDB instance), it catches the 
   specific error and falls back to non-transactional mode
5. Returns the result either way

The key insight is the isTransactionUnsupportedError() check - it has a list of known 
error messages that MongoDB returns when transactions aren't supported:
- "Transaction numbers are only allowed on a replica set member"
- "Transactions are not supported"
- Any message containing "replica set"

This means the code works on:
- Local MongoDB (development) - falls back, still works
- MongoDB 4.0 and earlier (legacy) - falls back, still works
- MongoDB Atlas (production) - uses transactions, maximum safety

The atomicity guarantees that concurrent orders are serialized by the database itself, 
not by application-level locking. This is the right abstraction.

Code structure demonstrates:
- Understanding of async/await and error handling
- Knowledge of MongoDB transaction semantics
- Pragmatic engineering (don't require transactions, but use them when available)
- Defensive programming (specific error detection, not broad catches)
- Proper session cleanup in finally block (prevents resource leaks)

This isn't a novel solution - many teams solve this the same way - but it's how you 
build reliable systems: prevent the obvious bugs first, then optimize. This prevents 
data corruption."

B) SIMPLE VERSION (for a non-technical interviewer):

"The best engineering decision I made was how I handle multiple orders trying to buy 
the same thing at the exact same time.

Imagine you have 5 units of a product in stock. Two customers order at the same instant. 
Normally, both orders would succeed, you'd sell 10 units but only had 5. Your inventory 
is wrong and your company loses money.

I solved this by using MongoDB transactions - think of it like locking a filing cabinet. 
When order 1 starts, it locks the product file. Order 1 reads: 5 units available. Order 
1 takes 5. File unlocked. Order 2 gets the lock, reads: 0 units available. Order 2 
fails, customer is told 'sorry, sold out.' No overselling.

The clever part: not all databases support locking. Some older systems or local 
development setups don't have this feature. Rather than crash or force everyone to 
upgrade, my code tries the locking approach first. If the database says 'I can't do 
that,' the code says 'okay, we'll do it the slower way,' and falls back to regular 
database operations. It's safer than the customer would have gotten without me trying, 
just not quite as safe.

This is what real-world software engineering looks like: be as safe as possible, 
gracefully handle older systems that can't do the safe thing, and make sure it 
actually works.

Why is this impressive? Because preventing one data corruption bug is worth more than 
adding 10 new features. Most developers add the next feature. Good engineers stop bugs."

C) WHY THIS IS IMPRESSIVE COMPARED TO THE NAIVE SOLUTION:

Naive solution (what most developers would do):
```
// Risky - race condition
let product = await Product.findById(productId);
if (product.stock >= quantity) {
  product.stock -= quantity;
  await product.save();
  // Create order
}
```

Better but still risky (app-level locking with mutex):
```
// Using a mutex - prevents concurrent access at app level
const mutex = new Mutex();
const release = await mutex.acquire();
try {
  let product = await Product.findById(productId);
  if (product.stock >= quantity) {
    product.stock -= quantity;
    await product.save();
  }
} finally {
  release();
}
```
Problem: Only works within a single Node.js process. If you have 2 servers, each has 
its own mutex, race condition still exists.

My solution (transactions):
```
// Database-level atomicity - works across all servers
await runWithOptionalTransaction(async (session) => {
  const product = await Product.findById(productId).session(session);
  if (product.stock < quantity) throw new Error('Insufficient stock');
  
  await Product.updateOne(
    {_id: productId},
    {$inc: {stock: -quantity}},
    {session}
  );
  
  await Order.create([{...}], {session});
});
```

Why my solution is better:
1. Database-enforced atomicity - works across multiple servers, even in load-balanced 
   environments
2. Proper rollback - if any operation fails, the entire transaction rolls back
3. Graceful fallback - if transactions aren't available, it detects that specifically 
   and falls back (not a broad try/catch)
4. No artificial locks holding connections - the database handles the locking
5. Works at scale - the database is optimized for this, better than app-level locks

This is the difference between "works most of the time" and "works correctly."
