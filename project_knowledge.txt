PROJECT IDENTITY
================================================================================
NAME: Inventory Management System
VERSION: 1.0.0
TYPE: Full-stack MERN (Monorepo with npm workspaces)
PRODUCTION READINESS: 9/10

WHAT IT IS:
Real-time inventory management platform for warehouses. Tracks products, orders, 
shipments, suppliers, and batches across multiple warehouses. Provides demand 
forecasting, anomaly detection, and live updates via WebSocket.

PROBLEM IT SOLVES:
- Warehouse inefficiency (reactive vs proactive inventory management)
- Manual stock tracking prone to errors and delays
- No predictive demand forecasting (leads to stockouts or overstock)
- Poor shipment visibility and routing
- Fragmented audit trail for compliance
- Manual anomaly detection (theft, data entry errors, system bugs)

TECH STACK:
Frontend:  React 18 + Vite + React Router v6 + Socket.IO client + Chart.js + Lucide React
Backend:   Node.js (ES modules) + Express.js + Socket.IO
Database:  MongoDB 6.0 (Atlas ready)
Auth:      JWT (30-day expiry) + Bcryptjs
Real-time: Socket.IO with rooms (not Redis adapter)
Email:     SendGrid
Logging:   Winston
Security:  Helmet + CORS + Rate Limiting + express-validator

RUNTIME ENVIRONMENT:
- Node.js 16+ required
- MongoDB 4.4+ (local or Atlas)
- Runs as separate frontend (port 3000) and backend (port 5000) or Docker
- Development: npm run dev (workspaces)
- Production: Docker containers + orchestration

FORECASTING SERVICE (forecastingService.js - 359 lines):
generateForecast(productId, options):
  1. Query historical sales data (aggregates from Order collection)
  2. Check minimum 3 months of data
  3. Run algorithm (default SIMPLE_MOVING_AVERAGE):
     - SMA: Average last 3 months
     - Weighted MA: Recent data weighted higher [0.5, 0.3, 0.2]
     - Exponential Smoothing: Alpha=0.3 iterative smoothing
  4. Calculate accuracy (MAPE - Mean Absolute Percentage Error)
  5. Calculate confidence interval based on accuracy
  6. Detect trend (positive/negative slope)
  7. Detect seasonality patterns (monthly variations)
  8. Generate recommendations (safety stock, reorder point, etc.)
  9. Save Forecast document
  10. Return complete forecast with all metrics

ANOMALY DETECTION SERVICE (anomalyDetectionService.js - 408 lines):
detectStockAnomalies(productId, options):
  1. Get products to analyze (single or all active)
  2. Query AuditLog for recent stock movements (STOCK_IN/OUT/TRANSFER)
  3. Calculate baseline statistics: mean, std deviation
  4. Run 3 detection algorithms:
     - Volume Anomalies: Z-score > 3 (3+ std devs from mean)
     - Frequency Anomalies: More movements/hour than baseline
     - Pattern Anomalies: Clustering or unusual timing (3am when closed)
  5. Create Alert documents for each anomaly
  6. Broadcast alerts via Socket.IO
  7. Return anomalies + count created

DATA FLOW
================================================================================

COMPLETE REQUEST FLOW (User creates order):

FRONTEND (React component):
1. User fills order form (product, quantity, shipping address)
2. onSubmit calls API POST /api/orders
3. AuthContext provides JWT token from sessionStorage
4. Fetch request includes:
   - Method: POST
   - Headers: Authorization: Bearer {token}, Content-Type: application/json
   - Body: JSON with order data
5. Send to backend at http://localhost:5000/api

BACKEND (Express):
1. Request hits middleware stack:
   - CORS middleware: Validates origin
   - express.json: Parses JSON body
   - morgan: Logs request
2. Route /api/orders POST handler executes
3. protect middleware:
   - Extracts token from Authorization header
   - Verifies signature with JWT_SECRET
   - Fetches User from MongoDB
   - Attaches req.user
   - If any fails, returns 401 Unauthorized
4. Input validation with express-validator:
   - Checks order type is PURCHASE or SALES
   - Checks items array is not empty
   - Checks each item has valid productId, quantity, price
   - Returns 400 Bad Request if validation fails
5. Business logic (with optional MongoDB transaction):
   - Starts MongoDB session if available (replica set)
   - For each item:
     - Query Product by ID
     - Check current stock >= requested quantity
     - Deduct stock from product
     - Create AuditLog entry (STOCK_OUT action)
   - Create Order document in MongoDB
   - If transaction available: Commit session
   - If transaction unavailable: Fall back to non-transactional (still creates records)
6. After order created:
   - Call global.emitShipmentUpdate(shipmentId, {status: 'CREATED', ...})
   - Socket.IO sends update to all connected clients in 'shipment-{id}' room
   - Socket.IO also sends to 'dashboard' room for global visibility
7. Return 201 Created with order object

REAL-TIME UPDATE (WebSocket):
1. Order created, backend calls global.emitShipmentUpdate()
2. Socket.IO server receives emit
3. Broadcasts to all sockets in 'shipment-{id}' room
4. Broadcasts to all sockets in 'dashboard' room
5. Frontend components have listeners:
   - Dashboard: socket.on('dashboard-update', (data) => setOrders(...))
   - Shipment detail page: socket.on('shipment-update', (data) => setShipment(...))
6. State updates, component re-renders
7. UI shows new order instantly (no page refresh needed)

DATA PERSISTENCE:
All changes written to MongoDB atomically (transactions where possible)
- Order document saved
- Product document updated with new stock
- AuditLog entries saved
- Shipment created (if order type is SALES)
All references maintained via ObjectId (Mongoose population)

ERROR HANDLING:
- Validation error → 400 Bad Request with error details
- Auth error → 401 Unauthorized
- Authorization error → 403 Forbidden
- Not found → 404 Not Found
- Server error → 500 Internal Server Error with logged details
- All errors logged with Winston (file + console)
- Frontend displays error toast to user


AUTHENTICATION & SECURITY
================================================================================

JWT TOKEN IMPLEMENTATION:
- Generated: jwt.sign({ id: userId }, JWT_SECRET, { expiresIn: '30d' })
- Stored: Frontend uses sessionStorage (NOT localStorage for security)
- Sent: Authorization: Bearer {token} header on every protected request
- Verified: jwt.verify(token, JWT_SECRET) with signature validation
- Expiry: 30 days from generation
- Claim: Only contains user ID (decoded to fetch user from DB)

PASSWORD SECURITY:
- Bcryptjs with salt rounds: 10
- Pre-save hook auto-hashes on User.save()
- matchPassword() method uses bcrypt.compare() for verification
- Passwords never logged or exposed in responses

ROLE-BASED ACCESS CONTROL (3 roles):
ADMIN: Full system access
  - Can create/delete users
  - Can approve all orders
  - Can access admin dashboards
  - Can manage system configuration

MANAGER: Operational access
  - Can create and approve orders
  - Can manage products and inventory
  - Can view analytics
  - Cannot manage users or system config

STAFF: Basic access
  - Can view inventory
  - Can create draft orders (not approve)
  - Can update stock counts
  - Limited report access

AUTHORIZATION PATTERNS:
protect middleware - Checks JWT validity, fetches user
authorize('ADMIN', 'MANAGER') - Checks role membership
admin middleware - Checks ADMIN role specifically

RATE LIMITING:
Login endpoint: 5 attempts per 15 minutes per IP
Uses express-rate-limit with IP-based tracking
Returns 429 Too Many Requests if exceeded

INPUT VALIDATION:
express-validator on all POST/PUT endpoints
- Type checking (string, number, integer, email, MongoId)
- Length validation (min/max characters)
- Pattern matching (regex for SKU format, email format)
- Enum validation (only allowed values)
- Sanitization (trim whitespace, normalize email)

KNOWN RISKS & GOTCHAS
================================================================================

RISK 1: MONGODB TRANSACTIONS NOT ALWAYS AVAILABLE
Problem: Transactions require MongoDB replica sets
Workaround: Code detects error and falls back to non-transactional mode
Impact: Order creation still works but lacks atomic guarantee
  - If process crashes after stock deducted but before Order saved,
    data is inconsistent (lost stock)
Solution: Use MongoDB Atlas (always has replica sets) or self-host with replica set
File: orderRoutes.js lines 22-50, isTransactionUnsupportedError()

RISK 2: SOCKET.IO MEMORY LEAKS
Problem: Socket connections are stateful, live in server memory
If users don't cleanly disconnect (close tab, bad network):
  - Connection object stays in server memory
  - After 1000+ connections, server runs out of memory and crashes
Solution: Properly handle disconnect events (server.js line 256-258)
Monitor socket count and implement forced cleanup after timeout
File: server.js lines 256-258

RISK 3: JWT_SECRET EXPOSED IN DEFAULTS
Problem: If .env not set, code could fall back to weak default
Security: validateEnv() prevents this - explicitly checks JWT_SECRET != default
File: validateEnv.js lines 57-59

RISK 4: NO HTTPS VALIDATION IN DEV
Problem: Development environment allows localhost (which is HTTP)
Security: Production env validation forces HTTPS domain
File: validateEnv.js lines 70-75

RISK 5: PAGINATION NOT ENFORCED ON ALL ENDPOINTS
Problem: Some GET endpoints return all records if limit not provided
Could cause OOM if 1 million products in database
Solution: Set default limit = 100, enforce max limit = 1000
File: productRoutes.js, orderRoutes.js (pagination implementation)

RISK 6: AUDIT LOG QUERYABLE WITH TIME COMPLEXITY
Problem: Audit logs can grow to millions of records
Slow queries on large time ranges without proper indexes
Solution: 4 strategic indexes configured (user+date, entity+date, action+date)
File: AuditLog.js lines 12-15

RISK 7: EMAIL SERVICE SINGLE POINT OF FAILURE
Problem: SendGrid down = no verification/password reset emails
Impact: Users cannot register or recover account
Solution: Implement email queue, retry logic, fallback provider
File: emailService.js (no retry logic currently)

RISK 8: NO INPUT SANITIZATION FOR XSS
Problem: User inputs stored in MongoDB could have HTML/JS
Displayed in frontend without escaping = XSS attack
Solution: React auto-escapes by default, but be careful with dangerouslySetInnerHTML
File: validators.js only validates format, not XSS sanitization

RISK 9: FORECASTING REQUIRES 3+ MONTHS DATA
Problem: New products have no sales history
Cannot forecast demand for new SKUs
Solution: Uses default static forecasts or manual entry for new products
File: forecastingService.js line 21-23

RISK 10: ANOMALY DETECTION Z-SCORE THRESHOLD FIXED AT 3
Problem: Threshold not adjustable per product
May miss subtle anomalies or create false positives
Solution: Add sensitivity setting (MEDIUM = 3, HIGH = 2, LOW = 4)
File: anomalyDetectionService.js line 11, could parameterize

RISK 11: NO RATE LIMITING ON NON-AUTH ENDPOINTS
Problem: Unauthenticated endpoints (health, public signup) can be DoS'd
Solution: Add rate limiting to all public endpoints
File: server.js, only login has rate limiting

RISK 12: SESSION STORAGE EXPOSED TO XSRF
Problem: Frontend stores JWT in sessionStorage + uses in fetch requests
XSRF attack could send authenticated request without CORS check
Solution: SameSite cookie attribute (currently using fetch, no cookies)
File: AuthContext.jsx line 70, sessionStorage.setItem('token')

RISK 13: NO HTTPS REDIRECT
Problem: Production can still be accessed via HTTP
Should force HTTPS
Solution: Add middleware to redirect HTTP to HTTPS or configure reverse proxy
File: server.js (no HTTPS middleware)

RISK 14: SENDGRID API KEY IN DOCKER COMPOSE
Problem: Dev credentials visible in docker-compose.yml
Could be checked into git by mistake
Solution: Use Docker secrets or environment file, not in compose
File: docker-compose.yml line 38, SENDGRID_API_KEY: test-key

RISK 15: NO RATE LIMITING ON SOCKET.IO
Problem: WebSocket can flood server with events
No backpressure or throttling
Solution: Implement rate limiting per socket connection
File: server.js, no rate limiting on socket events

GOTCHA 1: SOFT DELETES FILTER NOT AUTOMATIC
Problem: Forgot to add { deletedAt: null } in query
Returns deleted records in results
Solution: Add middleware to auto-add filter or use Mongoose plugins
File: productRoutes.js line 100, must manually add filter

GOTCHA 2: FORECAST SEASONALITY NEEDS 12 MONTHS MINIMUM
Problem: Set historicalPeriodMonths = 12 by default
Cannot detect seasonality with less data
Throws error if insufficient data
File: forecastingService.js line 21-23

GOTCHA 3: SOCKET.IO ROOMS NOT PERSISTED
Problem: If socket disconnects, room membership is lost
Reconnecting requires rejoin
Solution: Frontend should track rooms and rejoin on reconnect
File: InventoryContext.jsx, no reconnect logic visible

GOTCHA 4: ORDER STATUS STATES NOT SEQUENTIAL
Problem: Can set order status to any enum value without validation
Should only allow state transitions (PENDING → APPROVED → PROCESSING, etc.)
Solution: Add state machine validation
File: orderRoutes.js, no transition validation

GOTCHA 5: POPULATION DEPTH LIMITS
Problem: MongoDB populate with refs (order→items→product→supplier)
Deep nesting can cause N+1 query problem and slow performance
Solution: Limit population depth, use aggregate where needed
File: orderRoutes.js, check populate chain depth
